TEN Framework on arm64

在 aarch64 Linux 上執行與建置 TEN Framework 的實作手冊:這個 framework 由哪些東西組成、哪些部分跟 CPU 架構有關、每一部分怎麼建,以及出事的時候 怎麼查出真正的原因。

對應分支 feat/arm64-native-build。本文每一項陳述都經過原始碼對照或 實機執行驗證;凡是無法驗證的,文中會直接說明,而不是用推測填補。所有原始碼引用都附上 檔案與行號 —— 這些行號是撰寫當下重新核對過工作樹的結果,不是憑記憶寫的。

本文是 arm64_build.html 的繁體中文版, 內容一致。框架本身的專有名詞(extension、addon、 graph、runtime、binding、package 等)保留英文,與倉庫內既有的中文文檔慣例一致;檔名、函式名、設定鍵、日誌原文一律不譯。

第 I 部架構

1. 分層堆疊

一個 vendor extension 是純 Python 的,坐在四層之上。一項改動落在哪一層,決定了它用哪套 工具鏈建置、觸發哪個 CI job,以及它究竟跟 CPU 架構有沒有關係。

2. 倉庫的兩半

Framework coreAI agents
路徑core/、packages/、tests/、build/、third_party/、tools/ai_agents/
語言C/C++ runtime、Rust(ten_rust、ten_manager)、Go/Python/Node bindingPython extension、Go API server、Next.js playground
建置透過 tgn 包裝的 GN + Ninjatask targets
CIlinux_ubuntu2204.yml、mac_*、win.yml、tman_full_*ai_agents.yaml

兩組 CI 使用互斥的 paths-ignore 過濾:改 ai_agents/ 底下的東西永遠不會觸發 core 建置,改 core/ 底下的東西也永遠不會觸發 agents job。

本手冊大部分內容關於 agents 那一半。第 10 章是唯一一章在講怎麼建 core。

3. 訊息與路由

extension 之間從不互相呼叫。所有互動都是訊息,而 graph 的 connections 區塊決定誰會收到。這就是為什麼抽換一個 vendor 只是改 JSON —— 也是為什麼名字打錯會 無聲無息地失敗。

3.1 五種訊息型別

來源:core/include/ten_runtime/msg/msg.h

型別語意典型用途
cmd有回覆 —— 送出方會收到一個 CmdResulttool_register、on_user_joined
cmd_result回覆本身,由 runtime 負責配對不會手動路由
data單向、有結構asr_result、metrics、tts_flush_end
audio_frame單向,zero-copy 音訊緩衝pcm_frame
video_frame單向,視訊緩衝視覺類 extension

runtime 另外定義了內部命令 —— START_GRAPH、STOP_GRAPH、 CLOSE_APP、TIMER、TIMEOUT、 TRIGGER_LIFE_CYCLE —— 那是 framework 自己在用的。

3.2 connections 區塊,以及方向為什麼可以寫兩次

路由寫在 tenapp/property.json 的 predefined_graphs[].graph.connections 底下。每個區塊掛在一個 node 上, 以該 node 的 name 為鍵,不是以 addon 為鍵。方向來自 source(這些 node 送給我)或 dest(我送給這些 node)—— 兩種都 合法,所以同一條邊可以從任一端宣告。

3.3 三個名字必須一致

只有這三者全部吻合,extension 才會被實體化。不一致時,它會在 graph 載入階段無聲失敗 —— 沒有錯誤訊息,那個 extension 就是不存在:

  1. addon.py 裡 @register_addon_as_extension("x") 的引數
  2. 該 extension 的 manifest.json 中的 name 欄位
  3. graph node 的 addon 欄位

node 的 name 是另一回事:它是這個實例在 graph 內的標籤,也是 connections 用來路由的依據。抽換 vendor 時,改 addon, 不要動 name。

3.4 沒有路由的訊息會被丟棄 —— 而且那行警告是節流的

送出一個 graph 裡沒有對應連線的訊息,只會產生一行警告,其他什麼也不會發生。這行警告 很容易被錯過,原因從日誌上看不出來:它是按訊息名稱做速率限制的。

W ten:runtime ten_env_send_msg_internal@send.c:163
  Failed to send message: Failed to find destination of a 'data' message 'error' from graph.

這是真實案例。ASR extension 會送出一個 error data 訊息,但 websocket-example 的 graph 只路由了 asr_result、 metrics 和 tts_flush_end。因此少填一把 API key 這件事永遠傳不到 UI,只活在日誌裡。當介面什麼都沒顯示時,先 grep 這一行 —— 而且因為上面說的節流機制, 要 grep 整份檔案,不要只看尾巴。

4. RPC:cmd 與 CmdResult

來源:core/src/ten_runtime/binding/python/interface/ten_runtime/async_ten_env.py

cmd 是這個 framework 的 RPC。Python 側提供兩種形式。

單次回覆
result, err = await ten_env.send_cmd(cmd)
# runtime 保證 result.is_completed()
串流回覆
async for result, err in ten_env.send_cmd_ex(cmd):
    if err: break
    ...
    if result.is_completed(): break

send_cmd_ex 背後是一個 maxsize=10 的佇列,所以中間結果會 邊產生邊送達,最後一個帶著 is_completed()。LLM 逐 token 的輸出走的就是 這條路。

回覆
await ten_env.return_result(CmdResult.create(StatusCode.OK, cmd))
單向送出
await ten_env.send_data(data)
await ten_env.send_audio_frame(frame)
await ten_env.send_video_frame(frame)

每個都接受一個選用的 SendOptions;預設是送出即忘,而 wait_for_result=True 會等待 runtime 確認送達 —— 注意它回報的是「有沒有送到」, 不是「接收方拿它做了什麼」。

最花時間的兩個錯誤:

  • ten_env.get_property_*() 回傳的是 (value, error) 元組,不是值本身。永遠要取 [0]。
  • extension 不在主執行緒上跑,所以不能裝 signal handler,也不能用 atexit。清理work 寫在 on_stop() 裡。

5. runtime 如何載入 addon

來源:core/src/ten_runtime/addon/addon_autoload.c

一個 addon package 就是一個目錄。runtime 會掃描它的 lib/ 子目錄,並且 dlopen 在那裡找到的每一個 .so —— 它不會去 manifest 查 檔名,也不會跳過載入失敗的物件。

因此,帶原生程式碼的 extension 是兩份 JSON 加上 lib/*.so;純 Python 的 沒有 lib/,是透過 python_addon_loader 接到 runtime 的。

第 II 部平台

6. ABI 下限

官方發佈的 arm64 binary 有兩項性質,決定了它們到底能不能被載入。兩者都是用 readelf 對 0.11.71 的 ten_packages-linux-arm64-gcc-release.zip 讀出來的。

6.1 glibc ≥ 2.38

函式庫所需的最高 glibc 符號
libten_utils.so__isoc23_strtol@GLIBC_2.38
libpython_addon_loader.so__isoc23_strtol@GLIBC_2.38
libten_runtime.soGLIBC_2.34
libten_runtime_python.soGLIBC_2.17

同樣這幾個函式庫,x64 package 的上限停在 2.34。這個差異並不是刻意設計的: __isoc23_strtol 是 glibc 2.38 以上、搭配較新 GCC 時,標頭檔把 strtol 轉導過去的目標。它是 linux_arm64.yml 跑在 ubuntu-24.04-arm、而 linux_ubuntu2204.yml 跑在 22.04 的副產物,結果讓 arm64 的下限一口氣 拉高了四個 glibc 版本。

6.2 Python 版本必須與 binding 相符

ten_runtime_python 是針對某一個 Python 的標頭檔編出來的,而 python_addon_loader 是用一個寫死的檔名去 dlopen libpython。 在 arm64 上,這兩個版本不一樣。

tman check env 至今仍會回報 "TEN Framework only supports Python 3.10",並建議 pyenv install 3.10.18。就官方發佈的 arm64 package 而言, 這個建議是錯的 —— 照著做會得到一個 3.10 直譯器去配 3.12 的 binding。

只有第一項是真正的功能缺口。其餘列出來,是為了避免被誤認為缺口。

第 III 部建置

10. 從源碼建 framework core

四種情況需要這麼做:目標平台低於 ABI 下限、C runtime 本身要改、要跑 core 的測試, 或者要建一個 C++ extension。

core/ten_gn 是一個 submodule,而且剛 clone 下來時是空的 —— 沒初始化之前什麼都建不起來,而 tgn 本身就來自那裡:

git submodule update --init --recursive --depth 1 core/ten_gn
export PATH=$(pwd)/core/ten_gn:$PATH

它附帶 aarch64 版的 gn 與 ninja 執行檔,所以建置工具本身 不需要編譯。build.py:87 依 platform.machine() 選擇它們,而 validate_cpu 接受 linux/arm64,因此在 arm64 主機上不需要任何 額外旗標。

工具鏈:clang 或 gcc、cmake、Go ≥ 1.20、帶 cbindgen 的 Rust stable、 裝了 python-dotenv 和 jinja2 的 Python 3;Node 只有在建 tman designer 前端時才需要。相依清單見第 9 章。

根目錄的 Taskfile.yml 會偵測主機架構,所以在 arm64 上這樣就是建 arm64, 不用加旗標:

task gen
task build
# 輸出：out/linux/arm64/

若要完全比照 CI(.github/workflows/linux_arm64.yml,gcc + release):

tgn gen linux arm64 release -- \
  is_clang=false log_level=1 enable_serialized_actions=true \
  ten_enable_tests=false ten_rust_enable_tests=false ten_manager_enable_tests=false \
  ten_enable_libwebsockets=false ten_enable_cargo_clean=true \
  ten_enable_rust_incremental_build=false ten_manager_enable_frontend=false
tgn build linux arm64 release

與 x64 有兩處不同:arm64 CI 沒有啟用 ten_enable_ffmpeg_extensions,而且 把 ten_enable_libwebsockets 關掉。要重新打開任何一個,請先預留除錯時間。 覆蓋率則根本無法啟用 —— 見 8.1。

看起來風險最高的那幾塊,結果反而是可攜的。tman install 直接從 registry 解出 arm64 package。Go binding 連結 arm64 的 libten_runtime.so,乾淨地建 起來(GOARCH=arm64、GOARM64=v8.0)。所有 Python 相依都解到 aarch64 wheel —— pydantic_core、aiohttp、awscrt 以及其餘的都以 manylinux_*_aarch64 形式到位,沒有任何一個退回去做源碼建置。

12.3 Fedora 41+ 出貨的是 Python 3.13,不是 3.12

Ubuntu 24.04 剛好出貨的就是 arm64 binding 編譯所依據的 3.12,這也是為什麼 Ubuntu 那條 路完全不用處理版本問題。Fedora 41 之後預設是 3.13,所以要另外並存安裝 3.12:

sudo dnf -y install python3.12 python3.12-devel

Python 是可以多版本並存的,所以這麼做不會動到系統直譯器。

12.4 UV_PYTHON 必須釘住

症狀最沒有幫助的一種失敗,而且在 Ubuntu 上根本不存在。兩個相依安裝器都把 uv pip install --system 寫死了 —— tenapp 裡的 install_python_deps.py,以及 install_deps_and_build.sh 裡的 PIP_INSTALL_CMD —— 而 --system 選的是預設直譯器, 在這裡就是 3.13。相依裝進了 3.13 的 site-packages,而 runtime 透過 TEN_PYTHON_LIB_PATH 載入的是 3.12。安裝當下什麼都不會出錯;它會在很久以後, 以某個 extension 內的 ModuleNotFoundError 浮現出來。

export UV_PYTHON=/usr/bin/python3.12

12.5 uv pip install --system 需要 root

--system 會寫入 /usr/local/lib/python3.12/site-packages 及其 lib64 對應目錄。在容器裡看不到這個問題,因為容器是以 root 執行;在 裸機上以一般使用者身分執行時,task install 會在每一個 extension 上重試三次 後失敗,錯誤是 Permission denied (os error 13)。

只對那一個步驟提權。不要 sudo task install —— 那會連 bun install 和 go build 也以 root 跑,在使用者家目錄裡留下 root 所有的產物:

task install 會在那一步中止,所以它後面的兩個步驟必須手動補完 —— 或者用 finish_example_install_arm64.sh(19.5)。

/usr/local/lib/python3.12/site-packages 和它的 lib64 對應目錄都在 /usr/bin/python3.12 的預設 sys.path 上,所以 runtime 內嵌的直譯器找得到裝進去的東西。

已完整驗證:建出來的 extension 在 aarch64 主機上成功連上 Agora、發佈音訊軌,並開啟 資料串流。

14.1 RTC 是兩個 package,不是一個

這個區別造成的混淆,比本章其他任何東西都多。SDK 有 aarch64 版本這件事本身沒有讓你 前進一步:runtime 載入的那個物件是 wrapper,而 wrapper 正是那個「在你自己建出來之前, aarch64 版本並不存在」的東西。

Package它是什麼aarch64
agora_rtc_sdk(system)Agora 自家的 SDKAgora 有發佈;用 package_agora_rtc_sdk_arm64.sh 重新打包
agora_rtc(extension)runtime 真正 dlopen 的那個 wrapper從源碼建

14.2 aarch64 的 SDK 就是對的那一套

乍看之下,aarch64 的壓縮檔像是另一個產品:x64 package 的 109 個標頭檔中有 45 個不見了, 包括 IAgoraRtcEngine.h、IAgoraRtcEngineEx.h 和 IAgoraMediaEngine.h。x64 package 是從完整的 RTC SDK 組裝出來的;aarch64 壓縮檔則是 RTSA / server SDK。

符號分析顯示這不重要。x64 的 libagora_rtc.so 從 SDK 解析的符號正好 兩個:

createAgoraService      低階 / server 的進入點（IAgoraService.h）
getAgoraSdkVersion

它沒有直接引用任何 agora:: 類別符號 —— 其餘全部走 vtable —— 也從來沒有 碰過 createAgoraRtcEngine 或 IRtcEngine。這兩個符號都由 aarch64 版本匯出,以 nm -D 確認。wrapper 完全只用低階 API,而低階 API 正是 aarch64 壓縮檔所提供的東西。

那個壓縮檔在同一個函式庫之上附了兩套標頭檔,而函式庫匯出的 ABI 是 C 的:348 個 agora_* 函式、九個 create*/get* 工廠函式,以及 零個 C++ mangled 符號、vtable 或 typeinfo。C++ 介面照樣能用 —— createAgoraService() 回傳一個指標,對它的虛擬呼叫是透過物件自身的 vptr 派發的 —— 這就是為什麼只有兩個符號需要被解析。

14.3 版本配對

有兩個版本互相釘死,而搞錯這件事花掉的時間,比本章任何其他事情都多。

wrapper需要的 SDK
0.23.9-t1 —— 範例釘的版本=4.4.32-141
0.26.0-rc14 —— 撰寫當下的 master=4.4.32-175

釘成精確版本是有原因的。0.26 會呼叫 setTotalExtraSendMs 並覆寫 onCustomUserInfoUpdated;這兩個在 141 的標頭檔裡都不存在,所以拿 141 去建它會在編譯期失敗。改版本號沒有用 —— 缺的不是一個版本號。

向 Agora 索取 wrapper 源碼以及它 manifest 所釘的那個 SDK build,然後在動手建 任何東西之前,先確認配對:

strings <sdk>/agora_sdk/libagora_rtc_sdk.so | grep -oE '4\.4\.32\.[0-9]+' | sort -u

14.4 三處修改

沒有任何一處碰到 extension 的行為。

1. 宣告支援 arm64

manifest 出貨時 supports 只寫了 x64,所以 tman 不會把建出來的東西裝到 arm64 上。加上這一項,保留 x64:

"supports": [
  { "os": "linux", "arch": "x64" },
  { "os": "linux", "arch": "arm64" }
]
2. 從 resources 拿掉那個 x86-64 物件

BUILD.gn 會把 lib/liblinux_audio_hy_extension.so 打包進去, 而那個檔案只有 x86-64 版本。runtime 會 dlopen addon lib/ 底下 每一個 .so,所以架構不對的物件會讓載入失敗,而不是被跳過 (圖 4)。建 arm64 時把那一行拿掉;建 x64 時放回去。

3. 補上 #include <cstdint>

GCC 13 起不再遞移地引入 <cstdint>,而源碼在 27 個檔案 (0.23.9-t1)或 29 個檔案(0.26.0-rc14)裡依賴它。 這不是 arm64 的問題 —— 同樣的建置在 x64 上用 GCC 14 也會失敗 —— 值得回報上游。 要找出這些檔案:

for f in $(find src -name '*.h' -o -name '*.cc'); do
  grep -qE '\b(u?int(8|16|32|64)_t|uintptr_t|intptr_t)\b' "$f" &&
  ! grep -qE '#include\s*<c?stdint\.?h?>' "$f" && echo "$f"
done

  "video_frame_in": [], "video_frame_out": []
}

schema 在 core/src/ten_rust/src/json_schema/data/manifest.schema.json。只有三個頂層 欄位是必填的 —— type、name、version —— 而且 additionalProperties 是 false,所以無法辨識的鍵會被直接拒絕。 允許的頂層鍵為:type、name、version、 description、display_name、readme、 tags、dependencies、dev_dependencies、 api、supports、package、scripts。

改 api 就是改契約。新增一個 property 是相容的 —— 沒有人設定它,所以 套用預設值。拿掉一個,或改變它的意義,會在完全沒有錯誤訊息的情況下改變既有 graph 的行為。

實際的 extension 會把十個陣列全部宣告出來,包括空的,並用 ["**"] 當作 package.include。property 的型別有 string、 int32、bool、object、array。

15.2 C++ extension

骨架在 packages/core_extensions/default_extension_cpp/:

#include "ten_runtime/binding/cpp/ten.h"

class my_extension_t : public ten::extension_t {
  void on_init(ten::ten_env_t&) override;
  void on_start(ten::ten_env_t&) override;
  void on_cmd(ten::ten_env_t&, std::unique_ptr<ten::cmd_t>) override;
  void on_data(ten::ten_env_t&, std::unique_ptr<ten::data_t>) override;
  void on_audio_frame(ten::ten_env_t&, std::unique_ptr<ten::audio_frame_t>) override;
  void on_stop(ten::ten_env_t&) override;
};
TEN_CPP_REGISTER_ADDON_AS_EXTENSION(my_extension, my_extension_t);

送出一個音訊 frame:

auto frame = ten::audio_frame_t::create("pcm_frame");
frame->set_sample_rate(16000);
frame->set_number_of_channels(1);
frame->set_bytes_per_sample(2);
frame->set_samples_per_channel(n);

ten_env 只能從 extension 執行緒上碰。如果 vendor SDK 是在它 自己的執行緒上送資料進來,就必須透過 ten::ten_env_proxy_t 跳回來。搞錯這件 事會產生看起來很隨機、而且只在負載下才出現的當機。

ten_env_proxy_ = ten::ten_env_proxy_t::create(ten_env);   // 在 extension 執行緒上
…
// 從 SDK 執行緒 —— 先複製，SDK 可能立刻重用它的緩衝區
auto payload = std::make_shared<std::string>(static_cast<const char*>(pcm), bytes);
ten_env_proxy_->notify([payload](ten::ten_env_t &env) { … });
…
delete ten_env_proxy_;   // 它的解構子負責釋放；要在 on_stop_done() 之前做

ten_package() 會轉發 sources、 include_dirs、libs、lib_dirs、 ldflags、cflags*、configs、 defines、enable_build、output_name、 resources —— 但不會轉發 deps。GN 只會載入從根 target 可達的 BUILD.gn,所以 tenapp 裡的 extension 還需要在該 app 的 scripts/BUILD.gn 裡有一個 group 依賴它,否則它會被無聲地 永遠不建。

15.3 原生 extension 的維護成本高得多

純 Python 的 extension 是一份產物走遍所有平台。原生的則必須逐架構建置與發佈:

"supports": [{"os":"linux","arch":"x64"}, {"os":"linux","arch":"arm64"}]

漏掉哪一個,那個平台上的 dlopen 就會失敗 —— 結果是這個 extension 在該 平台上不存在,而不是功能少一點(圖 4)。這個不對稱性,就是第 14 章 存在的全部理由。

什麼時候該寫原生程式碼:要包裝一個既有的 C/C++ 函式庫時,或者 GIL 真的卡住音訊路徑 時。那 89 個 vendor extension 之所以是 Python,是因為它們講的是 HTTP 和 WebSocket,寫成 原生完全沒有好處。

16. 版本管理

版本宣告在四個地方,而它們之間只有一條箭頭是真正吃重的。

語法意義
"=0.23.9-t1"精確 —— 只接受這一個 build
"0.11"範圍 —— 最新的相容版本

對原生 SDK 做精確釘選是有實質作用的:沒有它,tman 會裝進一個 API 對不上的 SDK, 失敗點就從編譯期搬到執行期。

16.1 升級

沒有 tman upgrade 這個東西。除非傳 --locked,否則 tman install 會重新解析並改寫 lock 檔,所以:

  • 版本是精確釘選的 → 改 manifest.json,然後 tman install
  • 版本是範圍 → 光跑 tman install 就會拉到新的 build
  • 只要動一個 package → tman install extension <name>@<version>

永遠要確認動了什麼:

git diff tenapp/manifest-lock.json

16.2 用手放進去的 package 完全在這套機制之外

用手放進去的 extension —— 例如 arm64 上的 agora_rtc —— 沒有 .ten/package_info/,所以 tman 不知道它存在。tman install 不會 碰它,tman uninstall 也找不到它。升級意味著重建與重新複製:新的源碼、對得上 的 SDK、重新套用那三處修改、重建、放進去。

這就是走出套件管理器要付的代價,也是 14.6 節建議「想辦法讓這些 package 被正式發佈」 而不是長住在這裡的原因。

16.3 lock 檔說的比看起來少

被提交進版控的 manifest-lock.json 記錄的是產生它的那台機器上解析出來的 平台,不是這個 package 的平台支援矩陣。本倉庫每個範例的 lock 都寫著 {"os": "linux", "arch": "x64"},看起來像是硬性封鎖 arm64,其實不是 —— 同樣的版本是有發佈 arm64 的。

本倉庫沒有任何地方會傳 tman install --locked,所以每次安裝時 lock 都會 針對當下主機重新解析並改寫。要讀 registry,不要讀 lock 檔。

17. 配置:抽換 vendor、指向本地模型

17.1 設定放在哪裡

vendor 的設定放在 node 的 property.params 底下,是平的。沒有一層外殼去 標示模組名或 vendor 名 —— 本倉庫沒有任何程式碼在讀 {"asr": {"vendor": …}} 這種形狀。每個 extension 自己的測試設定檔才是權威; soniox_asr_python/tests/configs/property_en.json 具有代表性:

{
    "params": {
        "api_key": "${env:SONIOX_ASR_API_KEY}",
        "url": "wss://stt-rt.soniox.com/transcribe-websocket",
        "model": "stt-rt-v4",
        "language_hints": ["en"],
        "sample_rate": 16000
    }
}

抽換 provider 就是改 addon,並把該 node 的 params 整組換掉。 name 和 extension_group 不要動。

17.2 ${env:VAR} 有兩種失敗模式,而它們長得完全不一樣

runtime 在 core/src/ten_utils/lib/sys/general/placeholder.c 解析佔位符,並且會遞迴地 穿過 object 和 array(ten_extension_property_resolve_placeholders, core/src/ten_runtime/extension/internal/metadata.c),所以巢狀深度不影響。 真正有影響的是這個變數存不存在。

17.3 巢狀的鍵不會有任何警告

ai_agents/server/internal/http_server.go 會在啟動 worker 之前驗證 ${env:…},但那個迴圈只讀 node 的頂層 property,而且會跳過任何不是 字串的值。這些範例裡每一把 vendor 金鑰都住在 params 底下,而 params 是一個 object,所以它從來不會被檢查。少填或空的 vendor 金鑰,在任何 地方都不會產生 Environment variable not found 這一行。

verify_arm64_install.sh 補上了這個缺口 —— 請在開 session 之前跑它,而不是 事後從日誌裡推。

17.4 本地 LLM 通常不需要寫程式

openai_llm2_python 的第一個 property 就是 base_url:

{ "base_url": "https://api.openai.com/v1", "api_key": "${env:OPENAI_API_KEY}", … }

任何提供 OpenAI 相容 /v1/chat/completions 的本地服務 —— vLLM、Ollama 的 /v1 層、llama.cpp 的 llama-server、LM Studio、Xinference —— 都只是改一個欄位:

"property": {
  "base_url": "http://127.0.0.1:11434/v1",
  "api_key": "not-needed",
  "model": "qwen2.5:14b"
}

api_key 不能省略也不能是空的:多數本地服務不在乎它的值,但空字串會讓 extension 拒絕它 —— 又是 圖 9 的中間那一列。

只有在協定真的不相容時才寫新的 extension。骨架在 packages/core_extensions/default_llm_extension_python/ —— 28 行,其中唯一 必須實作的方法是 on_call_chat_completion,回傳 AsyncGenerator[LLMResponse, None]。基礎類別會處理訊息路由、工具協定,以及 與 main_control 之間的往返。

17.5 改動什麼時候生效

改了什麼生效時機
params 內的某個值(voice id、model、語言)下一個 session —— server 每開一個 worker 就重讀一次 property.json

兩套外形相同、要求相反的測試框架。真正有意義的區別是:vendor client 是不是真的。

兩者跑的都是真正的 TEN app 而不是樁:每個 conftest.py 都會在自己的執行緒 上啟動一個繼承 App 的 FakeApp,並且卡住 fixture 直到 on_init 被觸發,所以整個過程中 C runtime、Python binding 和 addon manager 都是活的。standalone 測試是對 extension 的單元測試,不是對 mock 的單元測試。

18.1 standalone 是怎麼跑的

<ext>/tests/bin/start:

export PYTHONPATH=.ten/app:.ten/app/ten_packages/system/ten_runtime_python/lib:…
export TEN_APP_BASE_DIR=.ten/app
pytest -s tests/ "$@"

.ten/app 是 tman -y install --standalone 產生的拋棄式 app 目錄樹,由 task test-extension 負責建立與刪除。 test-extension-no-install 兩件事都跳過 —— 迭代時比較快的迴圈,也是為什麼 殘留的 .ten/ 之後會造成莫名其妙的失敗 (rm -rf <ext>/.ten)。

mock 是在 extension import vendor client 的那個位置做 patch。以 soniox_asr_python 為例,那個位置是 soniox_asr_python.extension.SonioxWebsocketClient,被換成一個 MagicMock,它的 connect、send_audio、 finalize 和 stop 是 AsyncMock,另外還有 trigger_open、trigger_transcript、trigger_error、 trigger_close 和 trigger_finished 這些輔助方法,測試用它們把 extension 驅動到真實 vendor 會造成的各種狀態。十六個檔案涵蓋了 finalize 模式、重連、 信心值、多語輸出、句子終止、非法參數與 vendor 錯誤 —— 全都不需要金鑰。

-- 之後的東西會傳給 pytest:

task test-extension-no-install EXTENSION=agents/ten_packages/extension/soniox_asr_python -- -k test_finalize -s -v

18.2 guarder 是怎麼跑的

一套框架,以 extension 名稱參數化。它會先改寫自己的 manifest:

sed "s/{{extension_name}}/$EXT_NAME/g" manifest-tmpl.json > manifest.json
./scripts/install_deps_and_build.sh <os> <arch>
./tests/bin/start --extension_name <ext> --config_dir <ext>/tests/configs

install_deps_and_build.sh 在沒帶引數時會偵測主機架構,而 Taskfile 是明確 傳進去的,所以這條路在 arm64 上架構是正確的 —— 只是 CI 從來沒有在上面跑過。

--config_dir 指向 extension 自己的 tests/configs/,那是該 vendor 的權威 property 形狀。那些檔案帶的是真的 ${env:…} 佔位符,所以對應 的金鑰必須有設。

音訊素材是 tests/test_data/ 底下的 16 kHz PCM: 16k_en_us.pcm、16k_en_us_helloworld.pcm、 16k_zh_cn.pcm、16k_es_es.pcm。

tests/bin/start 預設排除 test_long_duration_stream。不要在 同一個容器裡同時跑 ASR 和 TTS guarder —— 它們的建置腳本會在共用的暫存路徑上打架。

18.3 core 的測試

arm64 job 把 ten_enable_tests=false 連同 rust、manager 的測試旗標一起設 掉,所以從來沒有任何測試 target 在 arm64 上被建出來過。要建它們就得從源碼建 core (第 10 章);產出的執行檔會落在 out/linux/arm64/tests/。覆蓋率無法啟用 —— 見 8.1。

18.4 測試日誌在哪裡

兩套框架都不寫檔案。兩個 conftest.py 都設成 {"emitter": {"type": "console", "config": {"stream": "stdout"}}} 並開在 debug 等級,所以想要一份檔案就自己接:

task test-extension EXTENSION=… 2>&1 | tee /tmp/ext_test.log

這跟執行中的 agent 是不同的去向 —— 在那邊,API server 會給每個 worker 一份自己的 檔案,放在 LOG_PATH 底下。測試執行從來不會寫到那裡。

19. 五個腳本

ai_agents/agents/scripts/ 底下有五個腳本。每一個都會驗證自己的產出,寧可 停下來也不會把壞掉的產物交給下一個。

19.1 verify_arm64_install.sh

檢查一個已安裝完成的 tenapp:包括 tman install 從 registry 拉下來 的東西,加上 task install 在本機建出來的東西。它不檢查從源碼建的 core。 結束碼是失敗檢查的數量,所以可以直接用在 CI 裡。

./verify_arm64_install.sh                  # 只做靜態檢查
./verify_arm64_install.sh --probe-worker   # 另外實際操作 Python binding
./verify_arm64_install.sh voice-assistant  # 換一個範例
區段檢查內容
0 主機架構、核心版本、ID/ID_LIKE/VERSION_ID、release 套件、glibc、gcc、套件管理器、SELinux、容器偵測、CPU、每一個 python3.x、每一個 libpython。斷言 glibc 下限與套件家族 —— 當 os-release 說不清楚時,改從 rpm 資料庫查。
1 環境TEN_PYTHON_LIB_PATH 與 UV_PYTHON,並推導出 runtime 將會內嵌哪一個直譯器
2 清點每一個 system package 與 extension 及其 manifest 版本、某個 graph 會實體化哪些 addon,以及每個 extension 的語言。graph 點名了但沒安裝的 addon,本身就是一項失敗。
3 架構每一個 shared object 的 ELF 架構,不是抽樣
4 連結未解析的 NEEDED 條目,並區分「這個函式庫根本不在目錄樹裡」(失敗)和「它存在但不在搜尋路徑上」(對被 dlopen 的 addon 而言是預期的 —— 會回報 RUNPATH 並說明原因)
5 glibclibten_runtime.so 實際要求的版本,對照主機提供的版本
6 Python ABIloader 預設的 libpython 名稱;分開探測 ten_runtime 與 ten_ai_base,好讓失敗能歸屬到真正壞掉的那一層,並原文印出例外
7 產物兩個在本機建出來的 Go 執行檔
7b 佔位符走過整個 graph 找 ${env:…},逐一對照 ai_agents/.env 解析,區分「缺席且必填」與「存在但為空」(圖 9),並在 .env 與環境變數不一致時據實回報,而不是自行挑一邊。從不印出任何值。
8 服務三個連接埠、/health、/graphs,以及處於 T 狀態的行程
8b worker 探測帶 --probe-worker 時,透過 API 開一個拋棄式 session 再停掉。不需要任何憑證:一個認證失敗的 worker,仍然已經載入了 libpython 並實體化了它的 extension。
9 worker 日誌libpython 載入失敗與 ModuleNotFoundError;在沒有任何 session 跑過時,回報 skip 而不是 pass

有兩項檢查之所以存在,是因為它們要抓的失敗在其他情況下完全無聲。第 8 段偵測處於 T 狀態的行程 —— 一個被丟到背景、又被 SIGTTOU 停住的 task run 會保留它的 listening socket,對連接埠檢查看起來很健康,實際上什麼都不收。第 9 段拒絕 回報一個它沒有掙來的 pass:一個沒有被實際操作過的 Python binding,不能當作它可用的證據。

總結會先陳述自己的適用範圍,再給結果。全綠代表的是:一個範例在這個架構上能安裝並 啟動 —— 一個 graph、一個拋棄式 session、沒有任何對話。

三個地方,而選錯是最浪費時間的事。其中一個 worker 的輸出究竟會落在哪裡,是執行期由 一個旗標決定的,不是你可以從磁碟上讀出來的設定。

位置內容什麼時候看
/tmp/task_run.log三個服務的 stdout。當 LOG_STDOUT=true 時,worker 的輸出也在這裡服務起不來、/start 失敗、WebSocket proxy 錯誤
$LOG_PATH/app-<channel>-<ts>.log每個 worker 一份(LOG_PATH 預設 /tmp/ten_agent)對話行為 —— 大多數問題
$LOG_PATH/property-<channel>-<ts>.json那個 session 使用的 graph 配置確認某個被注入的值

這一段不管哪種情況都能解出正確的檔案:

L=$(F=$(grep -o 'LogFile:[^ ]*' /tmp/task_run.log | tail -1 | cut -d: -f2); \
    [ -s "$F" ] && echo "$F" || echo /tmp/task_run.log)

管線的各個段落是以 node 名稱為鍵的,而抽換 vendor 時 node 名稱不會變:

grep -E '\[stt\]|asr_result|asr_error'          "$L" | tail -20
grep -E '\[llm\]|main_control'                  "$L" | tail -20
grep -E '\[tts\]|tts_audio_start|tts_audio_end' "$L" | tail -20

每一段裡第一個要讀的是 config: —— 那是這個 extension 實際收到的東西。 一把空的憑證,在其他所有地方看起來都跟能用的一模一樣。

key_point 是 extension 用來標記重要事件的日誌分類 (LOG_CATEGORY_KEY_POINT);grep 它就能得到整條管線的骨架。測試執行兩邊都不 會寫 —— 見 18.4。

21.1 服務起不來

被 SIGTTOU 停住。丟到背景的 task run 只要一碰終端機就會被停住。 nohup 擋的是 SIGHUP,不是這個。

ps -o pid,stat,cmd -p $(pgrep -f 'task run|bin/api|tman designer' | tr '\n' ',' | sed 's/,$//')

STAT 裡的 T 代表已停止。被停住的行程仍然保有它的 listening socket,所以連接埠檢查會回報它很健康,但它其實什麼都不收。

用 tmux:

tmux new -d -s ten 'cd <example> && task run 2>&1 | tee /tmp/task_run.log'

用 Ctrl+B 再按 D 卸離 —— 絕對不要按 Ctrl+C。

3000 埠被佔用。檢查 ss -tlnp | grep :3000 和 docker ps。一個在同一台主機上發佈 3000 埠的容器 —— 或者透過 WSL2 的 localhost 轉發能構到的容器 —— 會在你以為的那個位址上提供一個完全不同的應用。

前端立刻退出並抱怨 nmh:playground 的 node_modules 不見了。 見 19.5。

23. 值得推回上游的事

  • 把 agora_rtc 和 agora_rtc_sdk 發佈 arm64 版。 兩者今天都能為 aarch64 建置 —— wrapper 完全不需要改邏輯 —— 但兩個都不在 registry 裡, 所以每一個使用者都得自己建、自己用手放進去,活在套件管理器之外(16.2)。發佈它們就能 解開 26 個範例中的 24 個,而使用者端一行都不用改。
  • 在 agora_rtc 源碼裡補上 #include <cstdint>。 GCC 13 起不再遞移引入它,而源碼在 27 個檔案裡依賴它。這件事在現代工具鏈上也會弄壞 x64 的建置,所以它不是 arm64 的問題。
  • 提供 aarch64 版的 liblinux_audio_hy_extension.so,或者確認它已經 不再被使用。它目前只出貨 x86-64 版,必須從 arm64 package 裡排除 —— 而且因為 lib/ 是無條件掃描的(圖 4),把它留著會讓整個 extension 消失,不是只有那一項功能失效。
  • arm64 的 glibc 下限。把 linux_arm64.yml 改在 ubuntu-22.04-arm 上建,或者對著較舊的 sysroot 建,可以把需求從 2.38 降回 約 2.34,讓這些 package 在 RHEL 9、Amazon Linux 2023 和 Ubuntu 22.04 上可用。
  • Python 版本不一致。arm64 的 ten_runtime_python 是針對 3.12 建的, 而 python_addon_loader 預設是 libpython3.10.so (圖 5)。兩者應該有一個要動,好讓 TEN_PYTHON_LIB_PATH 變成不必要。
  • tman check env 的建議。它回報 Python 3.10 是唯一支援的版本, 這與 arm64 產物互相矛盾。
  • uv pip install --system 被寫死,導致裸機安裝需要 root。 install_python_deps.py 是把指令字面組出來的 (["uv", "pip", "install", "--system"]),沒有任何環境變數可以覆寫。在容器裡 這不用付代價 —— 它跑在 root 底下 —— 但以一般使用者身分執行時,每一個 extension 都會以 Permission denied 失敗。像 install_deps_and_build.sh 已經在做的 那樣尊重 PIP_INSTALL_CMD,就足夠了。
  • 沒有任何地方為相依安裝釘住直譯器。--system 解到的是 python3 當下指向的東西,而在任何出貨 3.13+ 的發行版上,那都不是 arm64 binding 編譯所依據的 3.12。這個不一致會一路無聲,直到某個 extension 在執行期丟出 ModuleNotFoundError。從 TEN_PYTHON_LIB_PATH 推導出直譯器 —— 版本號本來就寫在那裡面了 —— 就能補上這個缺口,而且不需要新增任何設定。
  • ${env:} 的驗證漏掉巢狀鍵。API server 只檢查 node 的頂層字串 property,而每一把 vendor 金鑰都住在 params 底下(17.3)。少填或空的金鑰, server 完全不會給出警告。
  • 無路由訊息的警告被節流到千分之一。對一條熱路徑來說這是正確的預設值,但它 造成的結果是:一個真的少了連線的 graph,只會在最開頭記錄這件事一次,之後看起來就一片 安靜(圖 3)。在 graph 拆除時補一行彙總 ——「名為 error 的訊息被丟棄了 n 次」—— 就能讓這個狀況被發現,而且完全不動到熱路徑。
  • ten_agent_build 是單一架構的。像 ten_building_ubuntu2204 那樣把它發佈成 multi-arch manifest,就能徹底不需要 Dockerfile.dev。
  • rustup target add stable x86_64-unknown-linux-gnuasan 被寫死在 multi-arch builder 的 Dockerfile 裡,在 arm64 上毫無意義。

24. 本手冊未涵蓋的部分

  • 從源碼建 core,在 arm64 上除了 CI 之外沒有被實際操作過。官方 job 會建它; 本手冊沒有獨立驗證過那個產物,而且從來沒有任何測試 target 在上面被建出來(18.3)。
  • guarder 測試組從來沒有在 arm64 上跑過。那條路的架構是正確的;那跟「跑過了」 不是同一件事。
  • ffmpeg 與 libwebsockets 在 arm64 的 core 建置中未經 測試。
  • build_docker_for_ai_agents.yml 建那 13 個範例映像時沒有帶 platforms: 欄位,所以它們都只有 amd64。
  • 並行與長時間執行的行為。這裡驗證過的一切,都是在一台閒置機器上的單一 session。
  • websocket-example 和 voice-assistant 之外的那 25 個 範例。它們的 extension 都是純 Python,graph 之間也只有配置上的差異,所以預期是可以 運作的 —— 但預期不等於驗證。
