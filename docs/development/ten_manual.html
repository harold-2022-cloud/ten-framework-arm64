第一部

理解架構

先建立正確的心智模型。這一部不需要動手，但沒有它，第三部的每個錯誤訊息都會像天書。

1TEN 是什麼

TEN 是一個即時多模態 AI agent 框架。它要解決的問題是：把語音辨識、大型語言模型、語音合成、 視訊、頭像這些各自獨立的服務，串成一條延遲夠低、可以真的跟人對話的管線。

它的核心設計決定是：agent 的行為由設定檔定義，不是由程式碼定義。你不寫「呼叫 ASR 然後呼叫 LLM」 這種流程程式碼，而是宣告一張圖（graph）：有哪些節點、節點之間傳什麼訊息。換 TTS 廠商是改 JSON，不是改程式。

這個 repo 有兩個半邊，工具鏈完全不同

這是理解一切的起點。搞錯自己在哪一邊，會用錯建置指令、看錯 log、查錯文件。

框架核心AI Agents
路徑core/ packages/ tests/ build/ third_party/ai_agents/
語言C/C++ 執行期、Rust（ten_rust、ten_manager）、Go/Python/Node 綁定Python extension、Go API server、Next.js 前端
建置系統GN + Ninja，透過 tgn 包裝task + tman + go build + bun

重要

兩套 CI 用互斥的 paths-ignore：改 ai_agents/ 不會觸發核心建置， 改 core/ 不會觸發 agent 測試。這也意味著你不需要為了跑 agent 而建置核心 —— 核心的產出可以從 package registry 直接下載。第三部會分開講這兩條路。

2執行期分層

一個廠商 extension（例如接 Deepgram 的語音辨識）坐在這個堆疊的最上層：

你寫的 Vendor Extension 純 Python。ai_agents/agents/ten_packages/extension/<name>/
registry ten_ai_base ASR / TTS / LLM / MLLM 的抽象基底類別 + api/*-interface.json 訊息契約
registry 語言綁定 ten_runtime_python / _go / _nodejs — C 擴充模組
core/ ten_runtime C/C++ 執行期：extension 生命週期、訊息佇列、graph 解析、執行緒模型
core/ ten_utils 基礎設施：記憶體檢查、log、字串、容器

這個分層決定了改動的成本。加一個新的 TTS 廠商只碰最上層，是純 Python 工作，不用編譯任何東西。 但如果你要改一個訊息型別、schema 或生命週期契約，就會伸進 core/，那是另一半邊的 repo， 另一套建置、另一套 CI。

在 repo 裡找不到 ten_ai_base 是正常的

ai_agents/agents/ten_packages/ 底下只有 extension/。 ten_packages/system/ten_ai_base 是 tman install 從 registry 拉下來的版本化依賴 （每個範例的 tenapp/manifest.json 裡寫著 {"type":"system","name":"ten_ai_base","version":"0.7"}）。 所以 docs/ai/ 裡引用的那些基底類別路徑，只存在於安裝後的 tenapp 內。 在乾淨的 checkout 裡 find 它們會是空的。

4Graph 與訊息路由

Agent 的行為定義在 ai_agents/agents/examples/<ex>/tenapp/property.json 的 predefined_graphs[]。一張 graph 有兩個部分：nodes（要實例化哪些 extension） 和 connections（訊息怎麼流）。

Graph 骨架tenapp/property.json
{
  "ten": {
    "predefined_graphs": [{
      "name": "voice_assistant",
      "auto_start": true,
      "graph": {
        "nodes": [
          {"type":"extension","name":"stt","addon":"deepgram_asr_python","property":{}},
          {"type":"extension","name":"llm","addon":"openai_llm2_python","property":{}},
          {"type":"extension","name":"tts","addon":"elevenlabs_tts2_python","property":{}}
        ],
        "connections": [ /* 見下 */ ]
      }
    }]
  }
}

四種訊息型別

型別承載常見名稱
cmd具名命令，有回應tool_register、on_user_joined、flush
data具名資料訊息asr_result、text_data、tts_text_input
audio_framePCM 音訊流pcm_frame（16-bit mono，16/24/48 kHz）
video_frame視訊流video_frame

典型語音管線的訊息流

agora_rtc
／websocket pcm_frame→ stt asr_result→ main text_data→ llm tts_text_input→ tts pcm_frame→ 傳輸層

這些訊息名稱不是自由字串，而是契約，宣告在 ten_ai_base/api/*-interface.json， 由每個 extension 的 manifest.json 匯入。

加 extension 進 graph 要改三個地方

1. tenapp/property.json 的 nodes[] 加節點 · 2. 同檔的 connections[] 接線 · 3. tenapp/manifest.json 加依賴（本地 extension 用 {"path": "../../../ten_packages/extension/<name>"}）

然後跑 task install。新增或移除 graph 需要完整重啟（前端會快取 /graphs 回應）；只改既有 graph 裡的值則是每個 session 重新載入，不用重啟。

5Server–Worker 模型

Go 寫的 HTTP server（ai_agents/server/）本身是無狀態的路由層。真正跑 agent 的是它為每個 session 生出來的 worker 行程。

Client→ Go server :8080 spawn→ worker（tman run start） 載入 graph→ extensions
端點方法作用
/healthGET健康檢查，回 {"code":"0"}
/graphsGET列出可用 graph
/startPOST為某個 channel 生出 worker
/stopPOST終止 worker
/pingPOST保持 session 存活
/listGET列出進行中的 session

Property 注入

/start 被呼叫時，server 會把動態值注入 graph：channel_name 灌進每一個宣告了 channel 屬性的節點，加上 startPropMap 的 remote_stream_id、bot_stream_id、token，以及請求裡 properties 指定的個別 extension 覆寫。

這個設計的意義是：新的 extension 只要宣告 channel 屬性就會自動拿到值，不需要改 server 程式碼。

對 Fedora ARM 是好消息

gn 和 ninja 是 tgn 自帶的 aarch64 預編二進位 （core/ten_gn/.gnfiles/bin/linux/arm64/），glibc 只需 2.17／2.18。 你不需要在 Fedora 上安裝 gn 或 ninja。

build.py 是依主機架構（os.uname().machine）挑 gn/ninja 的， 整個 repo 也沒有任何 sysroot 或 cross-toolchain 設定。CI 也只在原生 arm64 runner 上建 arm64。 所以 aarch64 的建置必須在 aarch64 機器上做 —— 你的 Fedora ARM 正好符合。

本地 registry

tman 的 registry index 支援 file:// scheme，可以在沒有網路或需要塞自訂套件時使用： 

mkdir -p ~/ten-localreg
cat > ~/tman-local.json <<'JSON'
{ "registry": { "default": { "index": "file:///home/<you>/ten-localreg" } } }
JSON

tman -c ~/tman-local.json publish          # 在套件目錄內執行
tman -c ~/tman-local.json -y install
關於 manifest-lock.json

committed 的 lockfile 的 supports 欄位只記錄產生它的那台機器所解析中的平台， 不是套件的完整平台矩陣。repo 裡每個 lock 都寫 linux/x64，那看起來像 arm64 被封死，其實不是。

而且整個 repo 都沒用 --locked，所以 tman install 會依主機平台重新解析並改寫 lock。 要判斷有沒有 arm64，看 registry，不要看 lock。

第三部

在 Fedora aarch64 上建置

從 git clone 開始。這一部有順序性 —— 每一步的驗證通過了再做下一步， 因為後面的錯誤幾乎都源自前面某一步沒真的成功。

11先確認環境

Fedora 對這個框架是相容的發行版，但有兩個 ABI 條件必須先確認。這些不是設定問題 —— 不符合的話官方二進位根本載不起來。 

uname -m                       # 必須是 aarch64
cat /etc/fedora-release
ldd --version | head -1        # glibc 必須 >= 2.38
python3 --version

條件一：glibc ≥ 2.38

官方 arm64 套件裡的 libten_utils.so 和 libpython_addon_loader.so 需要 __isoc23_strtol@GLIBC_2.38。（x64 套件只需 2.34 —— 這個落差是因為 arm64 CI 跑在 Ubuntu 24.04 而 x64 跑在 22.04，不是刻意的設計。）

FedoraglibcPython預編 arm64 套件
392.383.12可用
402.393.12可用，最順
412.403.13需另裝 python3.12
42+2.41+3.13+需另裝 python3.12

上表的 glibc/Python 對應是依 Fedora 各版本的已知組合。請以你機器上 ldd --version 與 python3 --version 的實際輸出為準。

條件二：Python 必須是 3.12

arm64 的 ten_runtime_python 是用 Python 3.12 標頭編的，而且不是 穩定 ABI。它的 74 個 Python 符號裡有 7 個是私有 API： 

_Py_Dealloc          _Py_NoneStruct      _Py_TrueStruct     _Py_FalseStruct
_PyArg_ParseTuple_SizeT   _PyObject_CallMethod_SizeT   _Py_BuildValue_SizeT

二進位裡沒有 Py_LIMITED_API／abi3 的跡象。所以它綁死 3.12， 不能指向 3.13。

在你的機器上驗證這件事

如果你在 Fedora 41+ 想確認 3.13 到底不行，直接查那些符號在不在： 

nm -D /usr/lib64/libpython3.13.so 2>/dev/null | grep -c _PyArg_ParseTuple_SizeT
# 回 0 → 確認不相容，必須裝 python3.12
Fedora 特有：TEN_PYTHON_LIB_PATH 是必填

python_addon_loader 用 hardcode 的檔名 dlopen libpython，候選路徑只有三個， 全部是 Debian／Ubuntu 慣例：

/usr/lib/aarch64-linux-gnu/libpython3.10.so · /usr/lib/libpython3.10.so · /usr/lib/x86_64-linux-gnu/libpython3.10.so

Fedora 把 64-bit 函式庫放在 /usr/lib64/，而且版本是 3.12 不是 3.10 —— 所以三個路徑一個都不會命中。在 Fedora 上這個環境變數不是選配： 

export TEN_PYTHON_LIB_PATH=/usr/lib64/libpython3.12.so
test -e "$TEN_PYTHON_LIB_PATH" && echo OK || echo "缺 python3-devel"

沒設的話錯誤訊息是 [Python addon loader] Failed to load system libpython.

tman check env 在 arm64 上會給錯建議

它會說 "TEN Framework only supports Python 3.10" 並建議 pyenv install 3.10.18。 對 arm64 的官方二進位而言這是錯的 —— 照做會得到一個 3.10 解譯器配上 3.12 編的 binding。 arm64 上正確答案是 3.12。

13Clone 與 submodule

最常見的第一個坑

core/ten_gn 是 git submodule，乾淨 clone 之後是空的。 而 tgn 這個建置工具本身就住在裡面 —— 沒初始化的話什麼都建不起來，錯誤會是 tgn: command not found 或 GN 找不到 //.gnfiles/build/options.gni。 

git clone git@github.com:harold-2022-cloud/ten-framework-arm64.git
cd ten-framework-arm64
git checkout feat/arm64-native-build

# 初始化 submodule（portal/ 除外，跟 CI 一致）
git submodule update --init --recursive --depth 1 core/ten_gn

# 讓 tgn 進 PATH
export PATH="$(pwd)/core/ten_gn:$PATH"

# 驗證
ls core/ten_gn/.gnfiles/bin/linux/arm64/       # 應該看到 gn 和 ninja
file core/ten_gn/.gnfiles/bin/linux/arm64/gn   # 應該說 ARM aarch64
tgn --help | head -3
驗收

tgn --help 有輸出，且那兩個二進位是 aarch64。這兩件事成立才往下走。

14建置核心

先想清楚你需不需要建核心。如果你的目標只是跑 agent，答案通常是不需要 —— 執行期套件可以由 tman 從 registry 直接下載 arm64 版（第 15 章）。 只有以下情況要自己建：

  • 你要改 C/C++ 執行期或語言綁定
  • 你的發行版 glibc < 2.38，官方二進位載不起來 —— 自己建就會連到你自己的 glibc
  • 你要自己編 tman

跟 CI 一致的建置（唯一在 arm64 上驗證過的組合）

export PATH="$(pwd)/core/ten_gn:$PATH"

tgn gen linux arm64 release -- \
  is_clang=false log_level=1 enable_serialized_actions=true \
  ten_enable_tests=false ten_rust_enable_tests=false \
  ten_manager_enable_tests=false ten_enable_libwebsockets=false \
  ten_enable_cargo_clean=true ten_enable_rust_incremental_build=false \
  ten_manager_enable_frontend=false

tgn build linux arm64 release

產出在 out/linux/arm64/：

路徑內容
out/linux/arm64/ten_packages/建好的執行期與 extension 套件
out/linux/arm64/ten_manager/bin/tman自建的 tman
out/linux/arm64/tests/測試二進位（上面的 flag 關掉了測試，所以不會有）
out/linux/arm64/app/範例 app
關於那些 flag

is_clang=false 是用 gcc。GN 的預設值是 is_clang=true （.gnfiles/build/BUILDCONFIG.gn），但 arm64 CI 用 gcc，所以那是唯一驗證過的路徑。 要用 clang 就把這個 flag 去掉，但要有除錯的預期。

arm64 CI 相對 x64 關掉了：全部測試、libwebsockets、tman designer 前端； 而且沒有開 ten_enable_ffmpeg_extensions（x64 有開）。這些組合在 arm64 上 沒有任何 CI 覆蓋，要開就預留除錯時間。

只想快速建 tman

task gen-tman     # 只開 ten_rust + ten_manager，不含語言綁定
task build-tman

用 Taskfile 的簡寫

根目錄的 Taskfile 會自動偵測主機架構，所以在 aarch64 上這樣就是建 arm64：

task gen
task build
task build BUILD_TYPE=release

注意這條路用的是 Taskfile 的預設 flag，不是上面 CI 那組。要完全對齊 CI 就直接呼叫 tgn。

已知的無關問題

在較新版的 task（實測 3.53.1）上，repo 根目錄的 task --list 會失敗， 訊息是 "Included Taskfiles can't have dotenv declarations"。這是既有問題（在未修改的 upstream 上也重現），因為根 Taskfile include 了帶 dotenv: 的 ai_agents/Taskfile.yml。在 ai_agents/ 目錄裡跑 task 是正常的， 直接呼叫 tgn 也不受影響。

15建置與執行 agent

這一段不需要先建核心。tman install 會依主機平台從 registry 拉 arm64 的執行期套件。

先選對範例

21 個範例裡有 19 個依賴 agora_rtc，而它沒有 arm64 版 （包裝層是預編 x86-64 且無原始碼）。在 arm64 上請用 websocket-example —— 它的原生依賴只有 TEN 自家那四個，傳輸層是純 Python 的 websocket_server。 

cd ai_agents
cp .env.example .env
# 編輯 .env 填入你的 provider 金鑰

# Fedora 必須設這個（第 11 章）
export TEN_PYTHON_LIB_PATH=/usr/lib64/libpython3.12.so

cd agents/examples/websocket-example
task install
task run

task install 實際做四件事：

tman install→ install_python_deps.py（uv）→ bun install（前端）→ go build -o bin/api

確認你真的拿到 arm64 而不是別的

file ai_agents/server/bin/api
# 應該說 ELF 64-bit LSB ... ARM aarch64

find ai_agents/agents/examples/websocket-example/tenapp/ten_packages \
  -name '*.so' | head -1 | xargs file
# 應該說 ARM aarch64

cat ai_agents/agents/examples/websocket-example/tenapp/manifest-lock.json \
  | grep -A2 supports
# 應該看到 "arch": "arm64"
驗收

curl -s http://localhost:8080/health 回 {"code":"0","data":null,"msg":"ok"}， 且 curl -s http://localhost:8080/graphs 列得出 graph 名稱。

lockfile 會被改寫

task install 會把 tenapp/manifest-lock.json 重寫成 arm64 條目。這是正確行為。 但那個檔案有進 git，commit 它會讓 x64 開發者下次 install 時平台被翻掉 —— 這是團隊要先講好的慣例。

第四部

排查建置錯誤

這個框架的錯誤會出現在好幾個不同的地方，而且經常不在你執行指令的那個終端機裡。 知道去哪裡看，比知道錯誤內容更重要。

16錯誤在哪裡看

按建置階段對應到該看的地方：

submodule / tgn 直接在終端機。tgn gen 失敗通常是 core/ten_gn 沒初始化，或 PATH 沒包含它。訊息會提到找不到 //.gnfiles/...。
GN 產生階段 終端機 + out/linux/arm64/ 下的 args.gn 與 build.ninja。 用 core/ten_gn/.gnfiles/bin/linux/arm64/gn args out/linux/arm64 --list 看實際生效的 flag 值（很多「為什麼沒開」的問題在這裡解決）。注意 gn 不在 PATH 上，它是 tgn 自帶的。
Ninja 編譯階段 終端機。加 -v 看完整編譯指令。out/linux/arm64/.ninja_log 有時間紀錄。 C/C++ 錯誤就是一般的 gcc/clang 輸出。
Rust（ten_rust / tman） cargo 的輸出會被 GN 包一層。訊息被截斷時直接進 core/src/ten_rust 或 core/src/ten_manager 跑 cargo build 取得完整診斷。
tman install 終端機。加 --verbose 會印出實際查詢的 registry URL 與解析過程 —— 平台解析錯誤（拿到 x64 而不是 arm64）在這裡才看得出來。
Python 依賴 終端機（uv 的輸出）。注意它會裝 tenapp 裡每一個 extension 的 requirements.txt，不只是你 graph 用到的那些。
Go server 終端機（go build）。ai_agents/server/ 底下可單獨跑 go build ./... 和 go test ./...。
執行期（agent 跑起來後） 這裡最容易漏。不在終端機，在 /tmp/task_run.log（若你用 > /tmp/task_run.log 重導）。extension 的 log 全部走這裡。
worker 崩潰 同上，但要找 bin/worker 相關訊息。設 TEN_ENABLE_BACKTRACE_DUMP=true 可取得 backtrace。

看執行期 log 的實用指令

tail -f /tmp/task_run.log

# 只看某個 extension
tail -f /tmp/task_run.log | grep --line-buffered "deepgram"

# 只看關鍵生命週期事件與廠商狀態
tail -f /tmp/task_run.log | grep -E "KEYPOINT|LOG_CATEGORY_VENDOR|config:"

# log 混了二進位導致 grep 抱怨時
strings /tmp/task_run.log | tail -n 100
log 分類

Extension 用 ten_env.log_info() 等方法輸出，並帶分類： LOG_CATEGORY_KEY_POINT（生命週期事件）、LOG_CATEGORY_VENDOR（廠商狀態）。 設定內容的 log 一律用 config: 前綴，QA 自動化會比對這個。

17常見失敗對照表

建置階段

症狀原因處理
tgn: command not found submodule 未初始化，或 PATH 沒含 core/ten_gn git submodule update --init --recursive --depth 1 core/ten_gn 後 export PATH=$(pwd)/core/ten_gn:$PATH
GN 找不到 //.gnfiles/build/options.gni 同上 同上。.gnfiles 是隱藏目錄，用 ls -a core/ten_gn 確認
task --list 在根目錄報 dotenv 錯 既有問題，與你的環境無關 在 ai_agents/ 裡跑 task，或直接用 tgn
C++ 標頭找不到（<coroutine> 等） 用了 clang 但沒裝 libcxx 加 is_clang=false 用 gcc（CI 驗證過的路徑），或裝 libcxx-devel
cargo 連結失敗 / 磁碟爆掉 Rust 平行連結吃掉大量磁碟 export CARGO_BUILD_JOBS=1，並加 ten_enable_cargo_clean=true
ten_enable_ffmpeg_extensions 相關失敗 Fedora 的 ffmpeg-devel 要 RPM Fusion，且 arm64 無 CI 覆蓋 別開它。預設就是關的

套件解析階段

症狀原因處理
解析到 x64 套件而不是 arm64 lockfile 記著 x64，或平台偵測有誤 tman install --os linux --arch arm64，或刪掉 manifest-lock.json 重解
agora_rtc 找不到相容版本 它沒有 arm64 版，這是預期的 改用 websocket-example
bin/worker: No such file or directory 裸的 tman install 把它刪了 用 task install 重建，不要用裸 tman install
ModuleNotFoundError: ten_packages.extension.X symlink 斷掉（常見於 guarder） ln -sf 補回，或重跑 tman install 讓它重建連結
task check 報一堆假的重新格式化 extension 目錄裡有殘留的 .ten/ rm -rf <ext>/.ten

執行期（Fedora 特別容易撞的）

症狀原因處理
[Python addon loader] Failed to load system libpython. hardcode 的三個候選路徑都是 Debian 慣例，Fedora 用 /usr/lib64 export TEN_PYTHON_LIB_PATH=/usr/lib64/libpython3.12.so
version `GLIBC_2.38' not found Fedora 版本太舊，低於 arm64 套件的下限 升級到 Fedora 39+，或自己從原始碼建核心
載入時 undefined symbol _Py* libpython 版本不是 3.12 裝 python3.12 並把 TEN_PYTHON_LIB_PATH 指向它
ValueError: signal only works in main thread Extension 裡用了 signal handler 或 atexit 改用 on_stop() 做清理
TypeError: '>' not supported between 'float' and 'tuple' get_property_*() 回的是 (value, error) tuple 取 [0]
前端起不來 / port 3000 被佔 next-server 是獨立行程，殺 node 和 bun 不夠 一併 pkill -9 -f next-server，並刪掉 playground/.next/dev/lock
graph 改了沒生效 新增／移除 graph 需要完整重啟；前端會快取 /graphs server 和前端都重啟

18驗證指令集

照順序跑，第一個失敗的地方就是問題所在。

### 0. 平台前提
uname -m                                          # aarch64
ldd --version | head -1                           # >= 2.38
python3 --version                                 # 3.12（或另裝 3.12）
test -e "${TEN_PYTHON_LIB_PATH:-/usr/lib64/libpython3.12.so}" && echo "libpython OK"

### 1. 工具鏈
tgn --help | head -3
tman --version
task --version
go version
uv --version
bun --version

### 2. tman 的環境判定（注意它對 Python 的建議在 arm64 上是錯的）
tman check env

### 3. submodule 與自帶工具鏈
git submodule status core/ten_gn                  # 開頭不該有 '-'
file core/ten_gn/.gnfiles/bin/linux/arm64/gn      # ARM aarch64

### 4. 核心建置產出（若有建）
ls out/linux/arm64/ten_packages/
file out/linux/arm64/ten_packages/system/ten_runtime/lib/libten_runtime.so

### 5. 生效的 GN flag
core/ten_gn/.gnfiles/bin/linux/arm64/gn args out/linux/arm64 --list \
  | grep -E "is_clang|ten_enable_(tests|libwebsockets|ffmpeg)"

### 6. agent 產出
file ai_agents/server/bin/api                     # ARM aarch64
grep -A2 supports ai_agents/agents/examples/websocket-example/tenapp/manifest-lock.json

### 7. 服務存活
curl -s http://localhost:8080/health
curl -s http://localhost:8080/graphs | jq -r '.data[].name'

### 8. 執行期 log
tail -n 200 /tmp/task_run.log
回報問題時該附上什麼

uname -m、cat /etc/fedora-release、ldd --version | head -1、 python3 --version、tman --version、失敗指令的完整輸出， 以及 /tmp/task_run.log 的相關片段。前四項能立刻排除掉這份文件裡一半的可能原因。
