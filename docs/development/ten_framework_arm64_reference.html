1.1 唯一的 prebuilt

整個建置系統只有一個二進位依賴不是源碼編的：

third_party/node/BUILD.gn
  ten_prebuilt_library("prebuilt_node_shared")
    node-shared-linux-arm64-gcc.zip / node-shared-linux-arm64-clang.zip

它有 arm64。 其餘 third_party（curl、zlib、mbedtls、msgpack、libuv、libwebsockets、 yyjson、nlohmann_json、googletest、ffmpeg）全部源碼編。

2. runtime 怎麼載入這些 .so

來源：core/src/ten_runtime/addon/addon_autoload.c

一個 addon 套件就是一個目錄。runtime 會掃描它的 lib/ 子目錄，把裡面每一個 .so 都 dlopen：

// addon_autoload.c:440
// Load the library from the 'lib/' directory.
success = load_all_dynamic_libraries_under_path(
    ten_string_get_raw_str(&addon_lib_folder_path));
tenapp/
└── ten_packages/
    ├── system/
    │   ├── ten_runtime/lib/          libten_runtime.so, libten_utils.so
    │   ├── ten_runtime_python/lib/   libten_runtime_python.so
    │   └── ten_runtime_go/lib/       libten_runtime_go.so
    ├── addon_loader/
    │   └── python_addon_loader/lib/  libpython_addon_loader.so   ← runtime 掃這裡
    └── extension/
        ├── agora_rtc/lib/            libagora_rtc.so             ← RTC 例子掃這裡
        │                             liblinux_audio_hy_extension.so
        └── soniox_asr_python/        （純 Python，沒有 lib/）

所以一個「有二進位的 extension」= manifest.json + property.json + lib/*.so。 純 Python 的 extension 沒有 lib/，走的是 python_addon_loader 那條路。

這解釋了為什麼架構不對就完全不能用。 dlopen 一個 x86-64 的 .so 到 aarch64 的進程裡會直接失敗 —— 不是功能降級，是那個 extension 根本不存在。

3. 缺的是什麼：誰用、誰編、誰連結

3.1 兩層，別搞混

TEN runtime (libten_runtime.so)
    │
    │ ① dlopen —— runtime 掃 extension/agora_rtc/lib/ 載入
    ↓
libagora_rtc.so                    ← TEN 的 wrapper（膠水層）
    │
    │ ② 呼叫 createAgoraService()
    ↓
libagora_rtc_sdk.so                ← Agora 的 SDK
    │
    │ ③ 連結
    ↓
libaosl.so, libagora-fdkaac.so, libagora-ffmpeg.so, libagora-soundtouch.so
誰在用它誰編譯它誰連結它aarch64
libagora_rtc.so TEN runtime，透過 dlopen Agora / TEN 維護者（源碼不公開） 它連結 Agora SDK 缺
libagora_rtc_sdk.so libagora_rtc.so Agora 被 wrapper 連結 上游有
缺的不是 SDK，是橋。 Agora 的 SDK 有 aarch64 版，但 SDK 完全不知道 TEN 存在 —— 它只是一套 C++ 函式庫。 把 TEN 的 extension 生命週期接到那套函式庫上的是 libagora_rtc.so， 而 TEN 真正 dlopen 的也是它。沒有這座橋，SDK 有 aarch64 也沒有東西會去呼叫。

3.2 為什麼不能自己編

編出 aarch64 的 libagora_rtc.so 需要它的 C++ 源碼。實際查證結果：

搜尋目標結果（third_party/ 以外）
createAgoraService無
IAgoraService無
IAgoraRtcEngine無
NGIAgoraRtcConnection無
agora::rtc無
名為 agora_rtc* 的源碼目錄不存在

推論的依據：wrapper 若在這個 repo 裡，必然會呼叫 createAgoraService() —— 那是它跟 SDK 溝通的唯一入口。整個 repo 一次都沒出現。 而發佈的 agora_rtc 套件只有四個檔：兩個 JSON 加兩個已編譯的 .so， 沒有 .cpp、沒有 BUILD.gn。

3.3 要 Agora 提供的最小集合

檔案理由
libagora_rtc.so (aarch64)runtime dlopen 的對象
liblinux_audio_hy_extension.so (aarch64)同套件內，一起被載入
libagora-ffmpeg.so (aarch64)x64 wrapper 的 NEEDED；aarch64 SDK tarball 沒有
libagora-soundtouch.so (aarch64)同上

libagora_stt_ag_extension.so、libagora_stt_ms_extension.so、 libagora_mcc_ysd_extension.so 是否需要，本文無法確認 —— 需要對 x64 的 libagora_rtc.so 執行 readelf -d 看 NEEDED 才能定案。

三種測試，能不能在 arm64 跑取決於它需要什麼。

4.1 extension 單元測試 —— arm64 上可直接跑

task test-extension EXTENSION=agents/ten_packages/extension/soniox_asr_python

能跑的原因：測試需要的東西 arm64 全都有 —— libten_runtime.so、libten_runtime_python.so、libpython_addon_loader.so 都是官方 arm64 build，extension 本身是純 Python，vendor client 被 mock 掉所以不碰網路。

<ext>/tests/bin/start 做兩件事：

export TEN_APP_BASE_DIR=.ten/app
export PYTHONPATH=.ten/app:.ten/app/ten_packages/system/ten_runtime_python/lib:...
pytest -s tests/ "$@"

.ten/app 是 tman -y install --standalone 產生的拋棄式 app tree， task test-extension 會先裝、跑完刪掉。快速迭代用 test-extension-no-install 跳過這兩步。

殘留的 .ten/ 會讓下一次 task check 報幻影格式問題、並讓 standalone 安裝失敗。 症狀奇怪時先 rm -rf <ext>/.ten。

測試不是在測 mock

conftest.py 會起一個真的 TEN app：FakeApp(App) 跑在自己的執行緒上， fixture 一直阻塞到 on_init 被呼叫為止。所以 C runtime、Python binding、addon manager 在測試期間全是活的，被換掉的只有 vendor 的 WebSocket client。

以 soniox_asr_python 為例，被 patch 的是 soniox_asr_python.extension.SonioxWebsocketClient，換成一個 MagicMock， 其 connect / send_audio / finalize / stop 是 AsyncMock， 另外提供 trigger_open、trigger_transcript、trigger_error、 trigger_close、trigger_finished 讓測試主動驅動狀態。 16 個測試檔涵蓋 finalize 模式、重連、信心值、多語言、句尾判定、無效參數、vendor 錯誤。

跑單一測試

task test-extension-no-install \
  EXTENSION=agents/ten_packages/extension/soniox_asr_python \
  -- -k test_finalize -s -v

-- 之後的參數原樣轉給 pytest。

4.2 guarder 整合測試

task asr-guarder-test EXTENSION=soniox_asr_python
task tts-guarder-test EXTENSION=elevenlabs_tts2_python

流程是：把 manifest-tmpl.json 的 {{extension_name}} 用 sed 換成實際名稱產生 manifest.json，跑 install_deps_and_build.sh <os> <arch>， 再以 --extension_name 和 --config_dir 啟動。

--config_dir 指向該 extension 自己的 tests/configs/ —— 那裡的 property_en.json / property_zh.json 是該 vendor 設定形狀的權威來源， 裡面帶真的 ${env:...}，所以對應的 key 必須設。

音訊素材：agents/integration_tests/asr_guarder/tests/test_data/ 下的 16k_en_us.pcm、16k_en_us_helloworld.pcm、16k_zh_cn.pcm、16k_es_es.pcm。

tests/bin/start 預設排除 test_long_duration_stream。 另外 ASR 和 TTS 的 guarder 不能在同一個容器裡並行 —— 兩者的建置腳本會搶同一個暫存路徑。

install_deps_and_build.sh 在不帶參數時會自己偵測架構，Taskfile 也會明確傳入， 所以這條路在 arm64 上是架構正確的。但 CI 從來沒有在 arm64 上跑過 guarder。

4.3 framework core 的測試

arm64 CI 的 tgn gen 帶了 ten_enable_tests=false、 ten_rust_enable_tests=false、ten_manager_enable_tests=false， 所以官方從來沒有在 arm64 上建過任何測試目標。

要自己跑的話得先從源碼建 core：

git submodule update --init --recursive --depth 1 core/ten_gn
export PATH=$(pwd)/core/ten_gn:$PATH
tgn gen linux arm64 release
tgn build linux arm64 release
# 產物在 out/linux/arm64/tests/

注意 enable_coverage 在 arm64 上不能開 —— 建置系統有六處 assert(is_linux && target_cpu == "x64") 擋著。

5. 訊息機制與路由

TEN 的 extension 之間不直接互相呼叫。所有互動都是訊息，由 graph 的 connections 決定誰收得到。這是「改 JSON 就能換掉一個 vendor」的原因， 也是「名字打錯就靜默失效」的原因。

5.1 五種訊息型別

來源：core/include/ten_runtime/msg/msg.h

型別語意典型用途
cmd有回覆，送出後會拿到 CmdResulttool_register、on_user_joined、工具呼叫
cmd_result上面那個的回覆，由 runtime 配對不需手動路由
data單向，結構化資料asr_result、metrics、tts_flush_end
audio_frame單向，音訊零複製緩衝pcm_frame
video_frame單向，視訊緩衝視覺類 extension

另外有幾個 runtime 內建的 cmd：TEN_MSG_TYPE_CMD_START_GRAPH、 CMD_STOP_GRAPH、CMD_CLOSE_APP、CMD_TIMER、 CMD_TIMEOUT、CMD_TRIGGER_LIFE_CYCLE，由框架自己用。

5.2 connections 的結構

路由寫在 tenapp/property.json 的 predefined_graphs[].graph.connections。 每個區塊掛在一個節點上（extension 欄位是節點的 name，不是 addon 名）， 底下按訊息型別分組：

{
  "extension": "main_control",        // 這個區塊在描述 main_control
  "cmd":  [ { "names": ["tool_register"], "source": [{"extension": "weatherapi_tool_python"}] } ],
  "data": [ { "name": "asr_result",       "source": [{"extension": "stt"}] } ]
}
方向由 source / dest 決定，兩個都可以用：
  • source —— 「這些節點送給我」（訂閱）
  • dest —— 「我送給這些節點」（發佈）
同一條鏈路寫在哪一端都成立，所以讀 graph 時兩邊都要看。

cmd 用 names（陣列，可一次綁多個），data / audio_frame 用 name（單數）。這個不一致是實際的寫法，照抄就好。

5.3 三個名字必須一致

一個 extension 要被 graph 實例化，這三處必須完全相同，否則載入時靜默失敗：
  1. addon.py 的 @register_addon_as_extension("x")
  2. 該 extension manifest.json 的 name
  3. graph 節點的 addon 欄位
節點的 name 則是另一回事 —— 它是這個實例在 graph 裡的代號， connections 靠它接線。所以換 vendor 時改 addon、不要改 name。

5.4 沒有路由的訊息會被丟棄

送出一個 graph 裡沒有對應 connection 的訊息，runtime 會警告然後丟掉：

W ten:runtime ten_env_send_msg_internal@send.c:163
  Failed to send message: Failed to find destination of a 'data' message 'error' from graph.

這是真實案例：ASR extension 送出 error 資料訊息，但 websocket-example 的 graph 只路由了 asr_result、metrics、tts_flush_end， 所以「API key 缺失」這個錯誤永遠到不了 UI，只留在 log 裡。 debug 時看到「沒反應」，先 grep 這行。

6. RPC：cmd 與 CmdResult

來源：core/src/ten_runtime/binding/python/interface/ten_runtime/async_ten_env.py

cmd 就是 TEN 的 RPC —— 送出後可以等回覆。Python 端有兩種型態：

單次回覆

result, err = await ten_env.send_cmd(cmd)
# result 是 CmdResult；runtime 保證 result.is_completed()

串流回覆

async for result, err in ten_env.send_cmd_ex(cmd):
    if err: break
    ...
    if result.is_completed(): break   # 最後一筆

send_cmd_ex 內部用 maxsize=10 的 queue，可以收多筆中間結果， 最後一筆帶 is_completed()。LLM 的逐字輸出就是走這條。

回覆方

await ten_env.return_result(CmdResult.create(StatusCode.OK, cmd))

6.1 單向訊息

await ten_env.send_data(data)                    # fire-and-forget
await ten_env.send_audio_frame(frame)
await ten_env.send_video_frame(frame)

三個都接受一個可選的 SendOptions：預設是射後不理， 帶 wait_for_result=True 則會等到 runtime 確認送達（拿到的是錯誤與否，不是回覆內容）。

兩個很花時間的陷阱：
  • ten_env.get_property_*() 回傳的是 (value, error) tuple，不是值本身。永遠取 [0]。
  • extension 跑在非主執行緒，不能裝 signal handler 或 atexit。清理寫在 on_stop()。

8. 串接本地大模型

8.1 先確認一件事：多數情況不需要寫 extension

openai_llm2_python 的 property.json 第一個欄位就是 base_url：

{
    "base_url": "https://api.openai.com/v1",
    "api_key": "${env:OPENAI_API_KEY}",
    "model": "${env:OPENAI_MODEL}",
    "max_tokens": 512,
    "prompt": "",
    "proxy_url": "${env:OPENAI_PROXY_URL|}"
}
本地模型只要提供 OpenAI 相容的 /v1/chat/completions，改一個欄位就好，不用寫任何代碼。 vLLM、Ollama（/v1 相容層）、llama.cpp 的 llama-server、LM Studio、Xinference 都提供這個介面。

graph 裡的 llm 節點改成：

{
  "type": "extension",
  "name": "llm",
  "addon": "openai_llm2_python",
  "extension_group": "chatgpt",
  "property": {
    "base_url": "http://192.168.0.14:11434/v1",
    "api_key": "not-needed",
    "model": "qwen2.5:14b",
    "max_tokens": 512,
    "prompt": ""
  }
}
api_key 不能省略也不能給空字串 —— 它在 manifest 的 property schema 裡是 string， 而多數本地伺服器不驗證這個值，隨便填一個非空字串即可。 若寫成 "${env:XXX}" 而該變數不存在，worker 會在 property 解析階段 exit(EXIT_FAILURE)（ten_utils/lib/sys/general/placeholder.c）。

改 property 內的值，下一個 session 生效；改 addon 或節點結構，要完整重啟 task run。

8.2 真的要寫一個新的 LLM extension

介面不相容時（自有協定、gRPC、特殊串流格式）才需要。骨架在 packages/core_extensions/default_llm_extension_python/，全文只有 28 行：

from typing_extensions import AsyncGenerator, override
from pydantic import BaseModel
from ten_ai_base.llm2 import AsyncLLM2BaseExtension
from ten_ai_base.struct import LLMRequest, LLMResponse
from ten_runtime import AsyncTenEnv


class DefaultLLMConfig(BaseModel):
    pass


class DefaultLLMExtension(AsyncLLM2BaseExtension):
    def __init__(self, name: str):
        super().__init__(name)
        self.config: DefaultLLMConfig | None = None

    @override
    async def on_call_chat_completion(
        self, ten_env: AsyncTenEnv, input: LLMRequest
    ) -> AsyncGenerator[LLMResponse, None]:
        raise NotImplementedError(...)

唯一必須實作的是 on_call_chat_completion，回傳一個 AsyncGenerator[LLMResponse, None] —— 逐段 yield 就是串流輸出。 基底類別負責訊息收發、工具呼叫協定、與 main_control 的往來，你不用碰。

可以覆寫的其他鉤子（參考 openai_llm2_python/extension.py）： on_init、on_start、on_stop、on_deinit、 on_retrieve_prompt。生命週期方法記得呼叫 await super().on_xxx()。

9. 分段驗證與日誌位置

一條 pipeline 壞掉時，先確定壞在哪一段。每一段有各自的驗證方式和各自的日誌， 混在一起看是找不到的。

9.1 日誌一共只有三個地方

位置誰寫的什麼時候看
/tmp/task_run.log
（自己 tee 出來的）		三個服務的 stdout：Next.js、tman designer、Go API server服務起不來、/start 失敗、WebSocket 代理錯誤
$LOG_PATH/app-<channel>-<ts>.log
預設 /tmp/ten_agent/		每個 worker 一個檔，由 Go server 指派對話行為不對 —— 九成的問題在這裡
$LOG_PATH/property-<channel>-<ts>.jsonGo server 為該 session 產生的 graph 設定想確認注入的值（ws port、channel）
測試的日誌不在上面任何一處。 兩種測試 harness 的 conftest.py 都把 log 設成 {"emitter": {"type": "console", "config": {"stream": "stdout"}}}、level debug， 沒有 file emitter。要留檔就自己 | tee。

9.2 六段驗證

第 1 段 · 環境與安裝

./ai_agents/agents/scripts/verify_arm64_install.sh --probe-worker

涵蓋架構、glibc、套件清單、每個 .so 的 ELF 架構、動態連結、Python ABI、 graph 的 ${env:} 佔位符、服務 port。日誌：stdout。

第 2 段 · 設定值有沒有真的進到 extension

grep -o "\[stt\] config: {.*" $(ls -t /tmp/ten_agent/app-*.log | head -1) | head -1

把 stt 換成 tts / llm。看到 'api_key': '' 就是 key 沒進去。 日誌：worker log。

第 3 段 · extension 單元測試（不需要 key、不連網）

task test-extension EXTENSION=agents/ten_packages/extension/soniox_asr_python

vendor 的 client 被 mock 掉（patch 掉 client 類別），測的是 extension 自己的行為。 tests/bin/start 設 TEN_APP_BASE_DIR=.ten/app 後跑 pytest -s tests/。 單跑一個測試：

task test-extension-no-install EXTENSION=... -- -k test_finalize -s -v

日誌：stdout。

第 4 段 · vendor 整合測試（需要真 key、會連網）

task asr-guarder-test EXTENSION=soniox_asr_python
task tts-guarder-test EXTENSION=elevenlabs_tts2_python

用真的 vendor client，設定取自該 extension 的 tests/configs/property_{en,zh}.json， 音訊素材是 agents/integration_tests/asr_guarder/tests/test_data/16k_{en_us,zh_cn,es_es}.pcm。 預設跳過 test_long_duration_stream。不要和 TTS guarder 同時跑 —— 兩者的建置腳本會搶同一個暫存路徑。 日誌：stdout。

第 5 段 · worker 起不起得來

curl -s localhost:8080/list

data 是空陣列就是沒有 worker。原因看：

grep -E 'handlerStart|Worker (start|stop|process)|placeholder' /tmp/task_run.log | tail -12

worker 死得夠早的話連自己的 log 檔都不會產生，那時只有 task_run.log 看得到原因。 日誌：task_run.log。

第 6 段 · pipeline 逐段

L=$(ls -t /tmp/ten_agent/app-*.log | head -1)
grep -E 'key_point|_error:|connection_status_changed|Failed to|Traceback' "$L" | tail -40
要找的意義
connection_status_changed ... 'current': 'connected'該 vendor 連上了
send asr_error / send tts_errorvendor 回報的錯，含 code 和 message
Failed to find destination of a ... messagegraph 少了一條 connection，訊息被丟棄
Tracebackextension 的 Python 例外

key_point 是 extension 標記關鍵事件用的 log category（const.py 的 LOG_CATEGORY_KEY_POINT），抓它等於拿到 pipeline 骨架。

9.3 一個代碼層的盲區

ai_agents/server/internal/http_server.go 會在 spawn worker 前檢查 ${env:...}， 但那段迴圈只讀節點 property 的頂層、而且只處理字串值。 各家 vendor 的 key 都埋在 property.params 裡，params 是物件， 直接被跳過 —— key 缺失或為空，這裡一句話都不會說。 verify_arm64_install.sh 的第 7b 段就是補這個洞。
