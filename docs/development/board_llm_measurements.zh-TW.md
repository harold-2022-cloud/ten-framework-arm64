# N1-655 板載 LLM：實測數據

給原廠討論用的數據。全部在同一塊板子上實測，沒有任何一項是從文件推論出來的；
不確定的地方都標出來。

英文版是 [`board_llm_measurements.md`](board_llm_measurements.md)。

## 量的是什麼

| | |
| --- | --- |
| 板子 | Ambarella N1-655，原廠 Fedora，`gcc-14.3.1-5.lch2025` |
| 模型 | `Deepseek-R1-Distill-Qwen` 7B，`n1-655_deepseek_r1_distill_qwen_7B_1NVP` |
| 啟動 | `run_llm_demo.sh --run_mode start --model_type 9 --ip 127.0.0.1 --max_user 1` |
| Client | `test_llm_client --port 9005 --model-type 9 --bsize 64 --user-num 1` |
| 介面 | HTTP POST 到 `127.0.0.1:8080`，SSE 回應，**一個 event 一個字** |
| 日期 | 2026-09-16、2026-09-17 |

兩種獨立量法，結果互相吻合：

1. **真實對話**，透過語音管線。應用程式記錄 POST 的時間、第一個答案字元的時間、
   最後一個的時間，以及答案長度。數 SSE 事件得到總字數。
2. **獨立探針**，走 raw socket，板子其餘閒置，計時 `</think>` 通過的時刻。

方法 1 的推理字數是 `SSE 事件數 − 答案字數 − 3`。那個 3 在每一輪都一樣，是標籤
周圍的框架。有另外從 transcript 取出推理原文的那幾輪，兩種量法一致：167 對 167、
172 對 172。

## 生成速率

板子**一個 SSE event 送一個字**，速率跟那個字是推理還是答案無關。

### 板子閒置時（探針，2026-09-17）

| 問題 | 總字數 | 總秒數 | 字／秒 |
| --- | ---: | ---: | ---: |
| 你是谁？ | 134 | 11.3 | 11.9 |
| 你是谁？ | 88 | 8.0 | 11.0 |
| 你是谁？ | 88 | 8.1 | 10.9 |
| 你是谁？ | 134 | 11.4 | 11.8 |
| 讲一个笑话。 | 563 | 56.4 | 10.0 |
| 讲一个笑话。 | 237 | 28.1 | 8.4 |

**8.4 – 11.9 字／秒，中位數 11.0。**

### 板子同時在跑語音時（真實對話，2026-09-16）

| 執行 | 輪次 | 總字數 | 總秒數 | 字／秒 |
| --- | --- | ---: | ---: | ---: |
| 10:20 | 1 | 186 | 19.0 | 9.8 |
| 10:20 | 2 | 240 | 24.7 | 9.7 |
| 11:41 | 1 | 186 | 37.4 | **5.0** |
| 11:41 | 2 | 223 | 25.4 | 8.8 |
| 11:41 | 3 | 560 | 55.1 | 10.2 |

那個 5.0 是一個 session 的第一輪，當時 ASR 正在補解 6.5 秒的音訊積壓、TTS 正在載
模型——兩個都是 CPU 上的 ONNX。到第三輪就回到 10.2。**這是單一樣本上的相關性，
不是已證實的因果**，也正是下面的問題之一：語音負載在 CPU 上，而 LLM 的推論在 VP 上。

## 時間花在哪

第一個答案字元之前的等待就是推理，而**推理長度取決於問題，不是答案**。

| 問題 | 推理字數 | 首個答案字元 | 答案字數 | 總計 |
| --- | ---: | ---: | ---: | ---: |
| 你是谁？ | 44 – 67 | 3.9 – 5.6 秒 | 44 – 67 | 8.0 – 11.4 秒 |
| 讲一个笑话 | 167 | 17.0 秒 | 16 | 19.2 秒 |
| 再讲讲一个 | 172 | 17.9 秒 | 65 | 24.9 秒 |
| 讲一个笑话 | 167 | 33.3 秒 | 16 | 37.6 秒 |
| 在再讲一个笑话 | 151 | 17.1 秒 | 69 | 25.6 秒 |
| 你可以解释四负ITY转换吗 | 370 | 36.3 秒 | 187 | 55.3 秒 |

最後一題是語音辨識把「你可以解释傅立叶转换吗」聽錯的結果。它產生了實測中最長的
推理，而答案把同一句話一字不差地重複了兩次。

**開放式問題下，使用者要等 17–36 秒才聽得到任何東西。** 答案本身只佔其中 2–19 秒。

### 推理不是鋪陳，而是答案本身

兩則笑話在推理階段就已經寫完了。第二輪的推理原文，172 字：

> 好，用户又让我讲笑话，我得再想一个简短有趣的。这次，我想到一个关于小明和数学的笑话。小明问数学老师：「为什么我们要学数学？」老师回答：「因为数学是科学的皇后，而科学是国家的基石。」小明听后，说：「那我以后当总统，数学就不是我的皇后了！」这个笑话既有趣又带点幽默，适合口语表达。再检查一下，有没有更合适的，但这个挺好的，应该可以满足用户的需求了。

接在後面的答案是同一則笑話的對話版。**使用者等了 17.9 秒，而模型大約在第 10 秒
就已經寫完了。**

兩輪推理的最後 42 個字完全相同：

> ，适合口语表达。再检查一下，有没有更合适的，但这个挺好的，应该可以满足用户的需求了。

每輪花 4.3 秒寫同一句話。

## 用 prompt 壓不下來

| Prompt 形式 | 問題 | 推理字數 | 對比基準 |
| --- | --- | ---: | --- |
| 基準 | 你是谁？ | 67 | |
| `/no_think ` 前綴 | 你是谁？ | 44 | 較短 |
| 「直接回答，不要思考过程。」前綴 | 你是谁？ | 44 | 較短 |
| 「直接回答，不要思考过程。」前綴 | 讲一个笑话。 | **523** | **是 167 基準的 3 倍** |

用中文明確叫它不要顯示思考過程，在開放式問題上**反而讓它想了三倍久**，花掉
51.2 秒。

第四種形式是在問題後面接 `\n<think>\n</think>`，在「讲一个笑话」上回報推理為零。
**那個量測不可信**：探針判斷推理結束的方式是在回應裡找 `</think>`，而那個形式
把 `</think>` 放進了請求，所以回顯和「模型真的跳過了推理」無法分辨。列出來只是
為了避免被當成結果。

## 併發與 session

`--max_user 1`，而且 session 在回覆之後還會**保留 180 秒**：

```
[INFO] 10:26:xx  From user: fd: 10, ... content: 讲一个笑话。
[ERR]  current user num (2) > max_user_num (1), please wait 180s to see if
       there are any timeout session.
[ERR]  handle_request_from_post fail
[INFO] 10:29:00  Dev session free: Dev VA: ..., fd_dev: 7, net_type: 9, sid: 2
```

所以每個請求都換新 `Session-Id` 的客戶端，**180 秒只能發一個請求**。重複使用同一個
`Session-Id` 搭配 `Reset-En: 1` 則可行，那也是應用程式實際的做法。

另外觀察到板子上跑著**兩個 `test_llm_client` 程序**，而手冊只有一個。兩者參數
相同、工作目錄相同。第二個是否佔著 user 名額未確認。

## 介面提供什麼

手冊上的四個 header：`Session-Id`（非零十進位整數，會被數值解析——非數值會被直接
關閉連線、連 HTTP 回應都沒有）、`Model-Type`、`Stream-Off`、`Reset-En`。
**沒有任何一個影響生成。** 沒有推理階段的設定、沒有長度上限、沒有停止條件。

回應是 `text/event-stream`，一個 `data:` event 一個字，空白字元以 `<SP>` 和 `<NL>`
轉義。推理以 `</think>` 結束，但**前面沒有對應的 `<think>` 開頭標籤**。

## 原廠答覆，2026-09-17

**推理階段可以繞過**，做在模型自己的 prompt 模板上，不是每個請求各自處理。
權重旁邊的 `prompt_config.json` 裡，assistant 標記結尾帶一個已經關閉的 think 區塊：

```json
"Symbol1": "<｜Assistant｜><think>\n\n</think>"
```

daemon 在載入模型時讀它，所以要重啟才生效。`tools/ambarella/set_llm_thinking.sh`
會做這個修改、先備份，用 `--on` 還原。

這跟上面第四種 prompt 形式是同一個想法，但做在沒有歧義的那一層：模板是在生成前於
伺服器端套用的，所以它不可能被回顯進回應裡、被誤認成結果。

**8–11 token/s 是這顆模型在 N1-655 上的預期值**，跟這裡量到的一致。

## 仍未解答的問題

1. **為什麼 host CPU 忙碌時速率會掉到 5.0 字／秒？** 推論不是在 VP 上嗎？
   關鍵路徑上有哪些 host 端的工作——tokenise、HTTP/SSE 層、還是餵 VP？

2. **180 秒的 session 保留可以縮短嗎？** 或是在回覆完成時明確釋放？在
   `--max_user 1` 之下，這正是第二個客戶端連不上的原因。

3. **`--max_user` 可以大於 1 嗎？** 每多一個 user 在記憶體和速率上的代價是多少？

4. **應該出現兩個 `test_llm_client` 嗎？** 如果不應該，是什麼留下了它，
   要怎麼安全地清除？

5. **缺少開頭的 `<think>` 是刻意的嗎？** 每個回覆都帶著結尾的 `</think>` 卻沒有
   開頭標籤，市面上針對這個模型家族的解析器一律會解錯。

## 如何重現

在這個 repo 裡：

```bash
tools/ambarella/check_llm_board.sh          # 拿板子比對手冊
python3 tools/ambarella/probe_llm_thinking.py --only "as deployed" --repeat 3
```

探針走 raw socket 而不是 HTTP 客戶端函式庫，因為板子的錯誤頁面沒辦法被函式庫解析。
它每個請求會報出思考時間、回答時間，以及兩邊的字數。
